## Overview

Session ops are your own hands on a running [session](/agents/sessions)'s sandbox, next to the agent: run a command, read or write a file, open an interactive shell, or put a port on a URL. Use them to inspect what the agent built, hand it inputs, fix something it got stuck on, or look at a dev server it started.

<Note>
Session ops are rolling out. Until they are enabled for your workspace, every route below answers `400` with "Session ops are not currently enabled." and an environment with `github_auth = true` is rejected.
</Note>

```bash
veri sessions exec 9f8e7d6c5b4a -- pytest -q tests/test_queue.py
veri sessions ls 9f8e7d6c5b4a /workspace/src
veri sessions cp ./fixtures.json 9f8e7d6c5b4a:/workspace/data/fixtures.json
veri sessions cp 9f8e7d6c5b4a:/workspace/report.md ./report.md
veri sessions attach 9f8e7d6c5b4a
veri sessions port 9f8e7d6c5b4a 3000
```

```python
from veri_sdk import Client

client = Client()
r = client.sessions.exec("9f8e7d6c5b4a", ["sh", "-c", "git status --short | head"])
print(r["exit_code"], r["stdout"])
client.sessions.write_file("9f8e7d6c5b4a", "/workspace/data/fixtures.json", open("fixtures.json", "rb").read())
report = client.sessions.read_file("9f8e7d6c5b4a", "/workspace/report.md")
print(client.sessions.list_files("9f8e7d6c5b4a", "/workspace/src")["entries"])
```

Every op needs the session `ready`: not while a run is in progress (`409`; wait for it or send `user.interrupt`), not while an approval is pending, and not while paused (resume it first). At most 30 ops per minute run on one session (`429` past that).

## Security model

- **The agent's user, never root.** Commands, file access and the shell run as the sandbox's unprivileged `agent` user (uid 1000), the same user the harness runs as. You can do what the agent can do, nothing more.
- **`/workspace` only.** Working directories and file paths must be `/workspace` or under it: absolute, no `..`. File paths are also resolved inside the sandbox, symlinks included, and refused (`400`) when they land outside `/workspace`, so a link the agent made to `/etc` or to the harness's own state does not leak it.
- **Egress still applies.** Network traffic from your commands and your shell goes through the same egress rules, secret swaps and `agent.egress` audit as the agent's. There is no bypass.
- **No real secrets in the sandbox.** Commands and shells get the session's environment variables as the agent sees them: plain values and secret placeholders, never the real value of a scoped secret and never the model credentials.
- **Audited.** Each op lands on the transcript: `session.exec` (argv and exit code; variable names, never their values), `session.file_read` and `session.file_write` (path and size, never content), `session.attach` and `session.detach` (who, how long, bytes moved), `session.port_open` and `session.port_close` (port and expiry, never the URL).

## Run a command

`POST /v1/sessions/{id}/exec` runs one command and waits for it.

| Field | |
| --- | --- |
| `argv` | The command and its arguments, 1 to 256 strings. No shell: use `["sh", "-c", "..."]` for pipes and redirects. |
| `cwd` | Working directory, `/workspace` (default) or a path under it. |
| `env` | Extra variables on top of the session's. `ANTHROPIC_*`, `OPENAI_*`, `VERI_*`, `PATH` and `LD_*` are dropped and listed in `env_dropped`. |
| `timeout_s` | 1 to 300 seconds (default 60). The command is killed at the deadline and `timed_out` is `true`. |

The response carries `exit_code`, `stdout` (at most 64 KiB), `stderr` (at most 16 KiB), `truncated` (either was cut), `timed_out`, `duration_ms` and `env_dropped`. A non-zero exit code is still a `200`: the command ran.

With the CLI, put `--` before the command so its options are not read as the CLI's: `veri sessions exec SID --cwd /workspace/app -e DEBUG=1 -- npm test -- --watch=false`. The CLI prints the command's output and exits with its exit code.

## Files

| Route | |
| --- | --- |
| `GET /v1/sessions/{id}/files?path=` | What the path is (`type`, `size`) and, for a directory, its entries (`name`, `type`; at most 1000, sorted). `path` defaults to `/workspace`. |
| `GET /v1/sessions/{id}/files/content?path=` | Download one regular file, `application/octet-stream`, at most 32 MiB (`413` above). |
| `PUT /v1/sessions/{id}/files/content?path=` | Upload the request body as the file, at most 32 MiB. Missing parent directories are created and an existing file is replaced; the file is owned by the agent user. |

Uploads larger than 32 MiB are not supported through this route. Fetch large inputs from inside the sandbox instead (`veri sessions exec SID -- curl -fsSLo /workspace/big.bin https://...`, which needs the host in the environment's [egress rules](/agents/environments#egress)), or attach them through a [volume](/volumes) on a training job.

`veri sessions cp` takes `SESSION_ID:/workspace/path` on exactly one side; a destination ending in `/` keeps the file's name, and `-` as the destination writes a download to stdout.

## Attach a shell

`veri sessions attach SESSION_ID` opens `bash` in a terminal inside the sandbox, as the agent user, in `/workspace`, with the session's environment. Exit the shell or press `Ctrl-]` to detach. The CLI needs the `websockets` package (`pip install websockets`).

- While a shell is attached the session stays awake and is billed like any awake time; it does not idle-pause.
- A shell with no input and no output for 30 minutes is closed.
- Each attach is a new shell: disconnecting ends the shell and anything running in its foreground. Start long jobs with `nohup ... &` if they should outlive the shell (they still stop when the session pauses).
- At most 4 shells per session at once.

Under the hood `POST /v1/sessions/{id}/attach-token` returns a `ws_url` that connects once, within 60 seconds. Append `&cols=120&rows=40` for the terminal size. Binary WebSocket frames are the terminal's input and output; a text frame `{"type":"resize","cols":120,"rows":40}` resizes it.

## Expose a port

`veri sessions port SESSION_ID 3000` (or `POST /v1/sessions/{id}/ports` with `{"port": 3000, "ttl_s": 3600}`) returns a URL like `https://3000-9f8e7d6c5b4a-<token>.<preview domain>` that reaches port 3000 inside the sandbox from any browser, WebSockets included.

- The token in the hostname is the permission: anyone with the URL gets through. Share it like a password.
- Links expire after `ttl_s` (60 to 86400 seconds, default 1 hour). `veri sessions port SESSION_ID 3000 --close` (or `DELETE /v1/sessions/{id}/ports/3000`) revokes one at once; opening the same port again issues a new token and retires the old one. At most 5 links per session.
- Ports 1024 to 65535. The process must listen on `0.0.0.0` or `localhost` inside the sandbox.
- The session must be running for the URL to answer (`503` while it is paused). Processes do not survive a pause, so restart the server after a resume.
- Preview traffic comes in from the internet and is not subject to the egress rules.

<Note>
Preview ports answer `501` with `preview_domain_not_configured` until the preview domain is set up on the platform.
</Note>

## GitHub access

Set `github_auth = true` on an [environment](/agents/environments) and every session started from it can use your GitHub account: `git clone`, `git push` and `gh` work against your private repositories.

```toml environment.toml
kind = "environment"
name = "repo-fixer"
github_auth = true

[model]
deployment_id = "1a2b3c4d5e6f"
```

- The token is the GitHub access of the person who starts the session (for a [trigger](/agents/triggers), the person who created it; for a fork, the person who forks), from their Veri sign-in with GitHub, which must include the `repo` scope. Starting a session without one fails with `400` `github_not_connected` and nothing is created: sign in to Veri with GitHub (or link GitHub to your account), grant repository access, and start it again.
- The token never enters the sandbox. The sandbox sees placeholders: `GITHUB_TOKEN` and `GH_TOKEN` for the GitHub API (`api.github.com`) and a git credential helper for `github.com`. The egress proxy replaces each placeholder with the real token only on requests to its own host; anywhere else the request is refused.
- Under the `coding` preset both hosts are already reachable. Under `locked_down`, add rules for `github.com` and `api.github.com`; a rule of your own (for example `GET` only) still narrows what the agent may do there.
- The token carries everything your GitHub account can do with the `repo` scope, for every repository. Give an agent your account only when you would give it your laptop.
