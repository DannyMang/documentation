Benchmarks are standard eval tasks that bring their own data, prompting, and scoring. You pick a task and a model; the platform handles the rest. Unlike dataset evals, a benchmark eval takes **no `dataset_id`**: the task supplies its own rows.

Benchmark runs are executed by [lm-eval-harness](https://github.com/EleutherAI/lm-evaluation-harness), the community-standard evaluation harness, pinned to a fixed version and run in an isolated sandbox against your deployment. Because the harness owns prompting and scoring, your scores are directly comparable with published lm-eval numbers for other models.

List the live catalog anytime:

```bash
veri evals benchmarks
```

Any lm-eval-harness task id works, not just the curated list. An unknown task id fails the run quickly with the harness's own error message.

## Running a benchmark

```bash
veri evals create --benchmark gsm8k --model deployment:dep_abc123 --n 100 --follow
```

Or in the dashboard: **Evaluations → + Create → Run a benchmark**.

Or via config:

```toml
kind = "eval"

[eval]
name = "gsm8k-checkpoint-7"

[[scorers]]
type = "benchmark"
name = "gsm8k"
task = "gsm8k"
sample_limit = 100

[run]
model = "deployment:dep_abc123"
```

A benchmark scorer cannot be combined with other scorers in the same eval: the task owns both the rows and the scoring.

## Results

The run's score is the task's primary metric (for example `exact_match,strict-match` for GSM8K). All metrics the harness reports, including alternate filters and stderr, are preserved under `results.harness.metrics`, and the harness version is recorded on the run for reproducibility. Per-sample prompts, responses, and scores are available in the run's items view, exactly like dataset evals.

## Sample limits

`sample_limit` caps how many rows run (`--n` on the CLI). The harness selects the same leading subset every time, so two runs with the same limit and seed score the same rows. Fewer samples = faster and cheaper; the full split gives the most stable score. For quick checkpoint comparisons, 50 to 100 samples is usually enough to see a meaningful gap.

## Sandboxed execution

The harness itself runs in an ephemeral, isolated sandbox that is created for the run and destroyed afterward. Code tasks (`humaneval`, `mbpp`) execute model completions inside that same sandbox, never on platform infrastructure, so a malicious or runaway completion cannot affect anything outside the run.

## Scoring notes

- Generation settings come from each task's published configuration (shot count, stop sequences, answer extraction), which is what makes scores comparable across models and with public leaderboards. Per-eval `generation_params` are not applied to benchmark runs.
- Multiple-choice tasks (`mmlu`, `arc_challenge`, `hellaswag`, and similar) are scored by answer loglikelihood and require the serving engine to expose prompt logprobs. Veri's standard vLLM deployments support this.
