`veri run <config.toml>` is a thin shortcut over the explicit `veri jobs create` / `veri deployments create`. It reads the required `kind` field from the config and dispatches.

The contract is plural-noun-verb (`veri jobs create configs/train.toml`); `veri run` exists to save typing on the common path.

## Scaffold a project: `veri init`

```bash
veri init my-project
# or, in the current directory:
veri init
```

`veri init NAME` writes 8 files into `./NAME`. With no `NAME`, scaffolds into the current directory.

```
my-project/
├── veri.toml                  # project marker: [project] name
├── reward.py                  # TRL-style reward function stub
├── configs/
│   ├── train.toml             # kind = "train": GRPO on GSM8K, L4-24GB x1
│   └── deploy.toml            # kind = "deploy"
├── datasets/
│   └── README.md
├── AGENTS.md                  # directory contract for coding agents
├── CLAUDE.md                  # one-liner: "See AGENTS.md."
└── .gitignore
```

The scaffolded `configs/train.toml` trains on a dataset named `gsm8k-train`. Register it once, then price the job before submitting it:

```bash
veri datasets connect-hf openai/gsm8k --config main --split train --map question=prompt --name gsm8k-train
veri jobs estimate configs/train.toml
```

By default `init` refuses to write into a non-empty directory. Use `--force` to scaffold alongside existing files (existing files are preserved):

```bash
veri init --force
```

## Dispatch rules

Every config starts with a required `kind` line:

```toml
kind = "train"    # or "deploy" or "environment"
```

`veri run <path>` reads `kind` and routes:

| `kind = ` | Dispatches to |
| --- | --- |
| `"train"` | `veri jobs create` |
| `"deploy"` | `veri deployments create` |
| `"environment"` | `veri environments create` (an [agent environment](/agents/environments): the TOML is the environment manifest) |

A missing `kind` errors and lists the valid values; an unknown value also prints a "did you mean" hint:

```bash
$ veri run nokind.toml
Error: config 'nokind.toml' is missing required `kind` field. Add one of: kind = "train" | "deploy" | "environment"
```

## Override TOML fields from the CLI

Use `--set <dotted.key>=<value>` to override any nested value. Convenience long-flags expand to `--set` internally.

```bash
# Submit a training run with two overrides:
veri run configs/train.toml \
  --set model.base=Qwen/Qwen3-8B \
  --set method.learning_rate=2e-6

# Convenience flag (jobs only), same as --set model.base=...:
veri jobs create configs/train.toml --base-model Qwen/Qwen3-8B
```

### Type coercion

Values parse as Python literals: integers, floats, `true` / `false`, quoted strings and lists. Anything else (including dates) stays a plain string. To force a string on a numeric-looking value, use `--set-string`:

```bash
veri jobs create configs/train.toml --set-string job.output_model=20260512
```

Without `--set-string`, `20260512` is sent as an integer and the API rejects it (`output_name: invalid type: integer`).

### Repeated flags build a list

```bash
veri jobs create configs/train.toml --set reward.files=../correctness.py --set reward.files=../format.py
# Results in reward.files = ["../correctness.py", "../format.py"]
```

### Conflict detection

The merger rejects a scalar where the config already has a table, and a sub-key under a path another `--set` made a scalar:

```bash
$ veri jobs create configs/train.toml --set model=foo --set model.base=bar
Error: --set conflict: 'model' is already a table; can't overwrite with a scalar
```

### Convenience long-flags

These flags are sugar over `--set` on `veri jobs create`:

| Flag | Expands to |
| --- | --- |
| `--base-model X` | `--set model.base=X` |
| `--gpu-type X` | `--set resources.gpu_type=X` |
| `--gpu-count N` | `--set resources.gpu_count=N` |
| `--dataset X` | `--set dataset.id=X` |
| `--reward X` | `--set reward.file=X` |
| `--region X` | `--set resources.region=X` |

`veri deployments create <config>` expands its flags the same way (`--name`, `--gpu-type`, `--gpu-count`, `--from-hf`, `--from-model`, and the replica and scaling flags); see [Create from a config](/cli/deployments#create-from-a-config).

## Config schemas

### `veri.toml` (project root)

```toml
# Project marker. Every config under configs/ is self-contained: the CLI
# does not read defaults from this file.

[project]
name = "my-project"
```

### `configs/train.toml` {#configs-train-toml}

```toml
kind = "train"

[job]
output_model = "my-tuned-model"

[model]
base = "Qwen/Qwen3-4B"

[dataset]
id = "gsm8k-train"      # a registered dataset's name or id

[reward]
file = "../reward.py"   # resolves against this config file's directory

[method]
type = "grpo"           # grpo | sft_text | dpo (grpo_agentic is being rebuilt; not currently available)
learning_rate = 1e-6
max_steps = 100
rollouts_per_prompt = 4
max_response_length = 512

[resources]
gpu_type = "L4-24GB"
gpu_count = 1
```

<Note>
  `[dataset].id` must reference an already-registered dataset, by name or id: register it first with `veri datasets upload` or `veri datasets connect-hf`. The trained model is saved to Veri storage. `[reward].file` is a local path (relative paths resolve against the config file's directory); the file's source is attached to the job at submit. Multi-reward: `files = ["a.py", "b.py"]` plus optional `weights = [1.0, 0.5]`.
</Note>

### `configs/deploy.toml` {#configs-deploy-toml}

```toml
kind = "deploy"

[deployment]
name = "my-endpoint"
model = "3f9c2a7b1d4e"      # training job id, HF repo, or saved model id
source = "training_job"     # training_job | huggingface | custom_model

[resources]
gpu_type = "L4-24GB"
gpu_count = 1               # GPUs per replica

[autoscaling]
min_replicas = 1            # 0 enables scale to zero
max_replicas = 1            # 1-8; above min_replicas enables autoscaling
# concurrency_target = 8
# scale_to_zero_window_seconds = 3600   # minimum 300
# idle_delete_after_days = 7
```

<Note>
  `[autoscaling]` accepts exactly `min_replicas`, `max_replicas`, `concurrency_target`, `scale_to_zero_window_seconds`, `idle_delete_after_days`, and `self_heal_attempts`; any other key (for example `target_qps`) is rejected. The same six keys are also accepted under `[resources]`, which is where the `veri deployments create` scaling flags (`--min-replicas`, `--max-replicas`, and friends) land. Setting a key in both tables with different values is an error: set it in one place.
</Note>

## Price a job before submitting

`veri jobs estimate` prices a `kind="train"` config without submitting it. It prints the resolved GPU config, a cost estimate, and, on the line under it, the duration it assumed (illustrative values):

```bash
$ veri jobs estimate configs/train.toml
┏━━━━━━━━━━┳━━━━━━━━━━━┳━━━━━━━━━━┳━━━━━━━━━━━━━━━━━━┳━━━━━━━━━━━━━━━━━━━┳━━━━━━━━━━━━━━━━━━━━┓
┃ gpu_type ┃ gpu_count ┃ provider ┃ duration_minutes ┃ rate_usd_per_hour ┃ estimated_cost_usd ┃
┡━━━━━━━━━━╇━━━━━━━━━━━╇━━━━━━━━━━╇━━━━━━━━━━━━━━━━━━╇━━━━━━━━━━━━━━━━━━━╇━━━━━━━━━━━━━━━━━━━━┩
│ L4-24GB  │ 1         │ aws      │ 36.0             │ 1.05              │ 0.63               │
└──────────┴───────────┴──────────┴──────────────────┴───────────────────┴────────────────────┘
Assumes 36 min: 6 min startup + 100 steps x 18 s/step. The step time was measured on one GRPO run
(Qwen2.5-1.5B LoRA, L4-24GB x1), not on this job; pass --minutes N to price your own duration.
```

The duration is an assumption, not a measurement of your job: about 6 minutes of startup (instance boot, environment setup, model and dataset download) plus `max_steps` at 18 seconds per step. Both numbers come from the measured GRPO run in [Training examples](/training/examples). Step time grows with model size, `rollouts_per_prompt`, response length and, for harness jobs, how long your agent takes per rollout, so treat the estimate as a floor for bigger runs. Without `max_steps` it assumes 100 steps (the GRPO default); an `sft_text` or `dpo` run without `max_steps` runs `num_epochs` over the dataset, which the estimate does not count.

Once you know your job's real duration (from a short run, or the wall time of a previous one), price that instead with `--minutes`:

```bash
veri jobs estimate configs/train.toml --minutes 90
```

Add `--format json` for the same fields as a JSON object (`gpu_type`, `gpu_count`, `provider`, `duration_minutes`, `rate_usd_per_hour`, `estimated_cost_usd`), plus `duration_assumption` with the sentence printed under the table. `--minutes` and the step-based duration need `veri-sdk` 0.2.45 or later; older CLIs priced `max_steps` as minutes.

The estimate covers GPU time only, not the flat checkpoint-storage charge on each billed job (see [Training job charges](/billing#training-job-charges)).

The estimate does not check the GPU shape or the dataset: submitting is what validates them. A submit that fails validation is rejected before anything is created or billed.
