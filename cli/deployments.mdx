The `veri deployments` group creates and manages inference endpoints. Each deployment exposes an OpenAI-compatible `/chat/completions` API backed by a Veri-trained or HuggingFace model.

## Deploy a Hugging Face model in one step

`veri deploy` is the shortest path from a Hugging Face repo to a live endpoint. It accepts a bare repo id or a pasted `huggingface.co` link:

```bash
veri deploy Qwen/Qwen3-4B
# or
veri deploy https://huggingface.co/Qwen/Qwen3-4B
```

In a terminal, it asks whether to cache the model in Veri storage for faster starts next time. Caching saves the downloaded weights to your [model library](/deployments/custom-models) in the background while the deployment serves; once the cached copy is ready, every later deploy of the same repo starts from Veri storage automatically instead of pulling from the Hugging Face hub.

| Flag | Purpose |
| --- | --- |
| `--name` | Endpoint name. Default: derived from the repo name (`qwen3-4b`). |
| `--gpu-type` | GPU shape. Default `A100-80GB`. |
| `--gpu-count` | GPUs per replica. Default `1`. |
| `--engine` | `vllm` (the default and only serving engine). |
| `--replicas` | GPU-box replicas behind the endpoint. Default `1`. |
| `--cache` / `--no-cache` | Cache the model in your library (or don't) without prompting. |
| `--yes` / `-y` | Skip the prompt. No caching unless `--cache` is passed. |
| `--vllm-image` | Explicit vLLM serving image for [architectures newer than the platform vLLM](/deployments#serving-newer-architectures), e.g. `vllm/vllm-openai:v0.25.1`. |
| `--trace-bodies` / `--no-trace-bodies` | Capture request/response bodies as browsable [traces](/deployments/observability#request-traces). Off by default. |
| `--trace-retention` | `base` (14 days, default) or `extended` (400 days). Requires `--trace-bodies`. |

Outside a terminal (scripts, CI) the prompt is skipped and caching stays off unless `--cache` is explicit.

`veri deploy` is sugar for `veri deployments create --from-hf`; every other lifecycle command below applies to the resulting deployment.

## Commands

| Command | Purpose |
| --- | --- |
| `create <config>` or inline | Bring up a deployment. |
| `list` | List deployments. |
| `get <id>` | Show one deployment. |
| `update <id>` | Change replica bounds / scaling settings on a live deployment. |
| `wake <id>` | Pre-warm a scaled-to-zero deployment. |
| `stop <id>` | Stop for good (terminal: cannot be resumed). Billing stops. |
| `delete <id>` | Permanently remove a stopped deployment and its request history. |
| `chat <id>` | Send a one-shot message for smoke testing. |
| `bench <id>` | Load-test the endpoint; report TTFB/TTFT/ITL/TPS/e2e at p50/p90/p99. |
| `metrics <id>` | RPS, latency, GPU utilization. |
| `requests <id>` | Recent inference requests. |
| `traces <id>` | Captured request traces (deployments created with `--trace-bodies`). |
| `trace <id> <trace-id>` | One trace with its full request/response bodies. |

## Create from a config

```bash
veri deployments create configs/deploy.toml
# or, via the hero verb:
veri run configs/deploy.toml
```

The config must declare `kind = "deploy"`. See the [config schema](/cli/run#configs-deploy-toml).

Flags passed alongside a config override the file's values the same way `--set` does (the flag wins). `--from-hf <repo>` and `--from-model <model-id>` replace `deployment.model` and pin `deployment.source` (`huggingface` / `custom_model`); `--gpu-count N` replaces `resources.gpu_count` (GPUs per replica, default `1`); `--name`, `--gpu-type`, and the replica and scaling flags below work the same way.

```bash
veri deployments create configs/deploy.toml --from-hf Qwen/Qwen3-4B --gpu-count 2
```

## Create inline

Two mutually exclusive modes — deploy a training job's output, or deploy a HuggingFace model directly.

```bash
# From a finished training job:
veri deployments create \
  --model job_abc \
  --name my-endpoint \
  --gpu-type A100-80GB \
  --gpu-count 1

# From a saved model in your library:
veri deployments create \
  --from-model mdl_abc \
  --name support-prod \
  --gpu-type A100-80GB \
  --gpu-count 1

# Directly from HuggingFace (no training):
veri deployments create \
  --from-hf Qwen/Qwen3-4B \
  --name qwen-prod \
  --gpu-type A100-80GB \
  --gpu-count 1
```

| Flag | Purpose |
| --- | --- |
| `--model <job-id>` | Deploy a training job's checkpoint. |
| `--from-model <model-id>` | Deploy a saved [custom model](/deployments/custom-models). |
| `--from-hf <repo>` | Deploy a HuggingFace repo. |
| `--name` | Display name. |
| `--gpu-type` | Required in inline form. |
| `--gpu-count` | GPUs per replica. Default `1`. |
| `--replicas` | GPU-box replicas behind one endpoint (1-8). Default `1`. Shorthand for equal `--min-replicas`/`--max-replicas`. |
| `--min-replicas` | Lower replica bound. Below `--max-replicas` enables autoscaling; `0` enables scale to zero. |
| `--max-replicas` | Upper replica bound (1-8). |
| `--concurrency-target` | In-flight requests per replica the autoscaler aims for. Default `8`. |
| `--scale-to-zero-window` | Idle seconds before a `--min-replicas 0` deployment parks. Default `3600`, minimum `300`. |
| `--idle-delete-after` | Auto-stop a parked deployment after N idle days. Default: keep it wakeable forever. |
| `--self-heal-attempts` | How many times Veri replaces the GPU box when the deployment's last box dies after it has served, `0` to `5`. Default `3`. See [Self-healing](/deployments#self-healing). Also available as `resources.self_heal_attempts` in a deploy config. |
| `--cache` / `--no-cache` | With `--from-hf` only: also save the downloaded model to your [library](/deployments/custom-models) so later deploys of the repo start from Veri storage. |
| `--vllm-arg` | Extra vLLM CLI token appended verbatim to the engine command; repeat per token (e.g. `--vllm-arg=--kv-cache-dtype --vllm-arg=fp8`). vllm engine only; platform-managed flags (`--model`, `--port`, `--host`, `--api-key`, `--served-model-name`) and `--trust-remote-code` are rejected. Also available as `deployment.vllm_extra_args` (list of strings) in a deploy config. |
| `--vllm-image` | Explicit vLLM serving image for [architectures newer than the platform vLLM](/deployments#serving-newer-architectures), e.g. `vllm/vllm-openai:v0.25.1`. Official upstream images only (`vllm/vllm-openai[-rocm]:<tag>`); vllm engine only. Also available as `deployment.vllm_image` in a deploy config. Default: platform vLLM. |
| `--trace-bodies` / `--no-trace-bodies` | Capture this deployment's request/response bodies as browsable [traces](/deployments/observability#request-traces). Off by default: enabling stores your end users' prompt/completion content. Also available as `deployment.trace_bodies` in a deploy config. |
| `--trace-retention` | Trace retention class: `base` (14 days, default) or `extended` (400 days, extended rate). Requires `--trace-bodies`. Also available as `deployment.trace_retention`. |

See [Replicas, autoscaling, and scale to zero](#replicas-autoscaling-and-scale-to-zero) for how the bounds behave.

## Smoke-test with `chat`

The fastest way to confirm a deployment is healthy:

```bash
veri deployments chat dep_abc --message "What is 2+2?"
```

The CLI calls the OpenAI-compatible endpoint with a single user message and prints the assistant's reply.

| Flag | Purpose |
| --- | --- |
| `--message` / `-m` | Required. The user message. |
| `--model` | Override the model name in the request body. Defaults to the deployment's name. |
| `--temperature` | Sampling temperature. Default `1.0`. |
| `--max-tokens` | Cap on response tokens. |
| `--session-id` | Pin this conversation to one replica for cache-warm affinity (sets the `X-Veri-Session-Id` header). Only affects multi-replica deployments. Experimental. |

For programmatic chat, use `https://api.veri.studio/v1/deployments/{id}` as the OpenAI-compatible `base_url` with your Veri API key. The deployment's `endpoint_url` (visible in `veri deployments get`) is that same platform URL with `/chat/completions` already appended, for direct HTTP calls.

## Replicas, autoscaling, and scale to zero

One endpoint can be served by several GPU boxes behind a load-balancing router. The replica bounds decide how the fleet behaves:

| Bounds | Behavior |
| --- | --- |
| `--replicas N` (or equal min/max) | Fixed fleet of N boxes. |
| `--min-replicas` below `--max-replicas` | Autoscaling: the fleet grows and shrinks with load. |
| `--min-replicas 0` | Scale to zero: the fleet also parks entirely when idle and wakes on demand. |

```bash
# Fixed fleet of 2:
veri deployments create \
  --from-hf Qwen/Qwen3-4B --name qwen-prod \
  --gpu-type L4-24GB --gpu-count 1 \
  --replicas 2

# Autoscale 1-4 boxes, park after 30 idle minutes:
veri deployments create \
  --from-hf Qwen/Qwen3-4B --name qwen-dev \
  --gpu-type L4-24GB --gpu-count 1 \
  --min-replicas 0 --max-replicas 4 \
  --scale-to-zero-window 1800
```

The deployment reports `serving` once at least one replica is up. `list` and `get` show the fleet as `ready/desired` (for example `2/3` while a scale-up is still provisioning). A replica that dies is replaced automatically; the deployment keeps serving at reduced capacity in the meantime. If the last box dies, the deployment shows `provisioning` (with `failure_code` `replica_lost`) while Veri replaces it, up to `--self-heal-attempts` times; see [Self-healing](/deployments#self-healing).

### Autoscaling

With `min-replicas` below `max-replicas`, the fleet targets `--concurrency-target` in-flight requests per replica (default 8). Scale-up is fast (within about a minute of sustained load); scale-down is deliberately slow (about 15 minutes of sustained low load per step) because a wrong scale-down costs a multi-minute GPU boot. Lower the target for latency-sensitive chat; raise it for batch throughput. When scaling down, replicas that are still loading (not yet serving) are removed first; a serving replica is only drained once there is no loading replica left to cancel.

### Scale to zero

With `--min-replicas 0`, a deployment idle past `--scale-to-zero-window` (default 1 hour) parks: replicas terminate, billing stops, status becomes `scaled_to_zero`. The idle window counts from when the deployment starts serving or from its last request (not from create or wake), and a park waits for in-flight requests to finish and for a fresh engine-metrics sample before terminating anything. Turning scale-to-zero on, or changing the window, starts a fresh idle window. The next chat request wakes it. While the GPU boots (a few minutes), the server answers that request with `503`, a `Retry-After` header, and error code `deployment_waking`. The SDK and CLI absorb this for you: `veri deployments chat` prints a "waking from zero" note and waits for the answer, and the Python SDK's `chat()` retries in the background until the deployment is up (see [chat and waking](/deployments/api#post-v1deploymentsidchatcompletions) for the knobs). Only raw HTTP clients need to handle the `503` themselves. To hide the cold start from your users, pre-warm on a predictive signal instead:

```bash
veri deployments wake dep_abc     # 202; no-op if already up
```

Then poll `veri deployments get dep_abc` until it's `serving`. Raising the floor also wakes it: `veri deployments update dep_abc --min-replicas 1` on a parked deployment wakes it immediately. A wake (explicit, request-triggered, or from raising `--min-replicas`) relaunches `min_replicas` boxes (at least one; the autoscaler grows the fleet again if traffic returns) and is subject to the workspace active-replica limit, like a create: with no headroom it returns `429` with code `ACTIVE_DEPLOYMENT_LIMIT` and the deployment stays parked, so stop or scale down something else first. Optionally set `--idle-delete-after N` to auto-stop a deployment that stays parked with no traffic for N days.

### Change scaling on a live deployment

```bash
veri deployments update dep_abc --replicas 4                    # fixed fleet of 4
veri deployments update dep_abc --min-replicas 1 --max-replicas 6
veri deployments update dep_abc --concurrency-target 4
veri deployments update dep_abc --min-replicas 1                 # parked: wakes it now
veri deployments update dep_abc --self-heal-attempts 5           # replace a lost last box up to 5 times
```

`update` returns immediately with the new desired state; the fleet converges in the background (watch the `replicas` column approach `desired/desired`). Model, GPU, and provider are immutable — recreate the deployment to change those.

- **Parked (`scaled_to_zero`):** raising `--min-replicas` to 1 or more wakes the deployment immediately and boots the new floor, like `veri deployments wake`. It is checked against the workspace active-replica limit first: if the new floor does not fit, `update` fails with `429` (`ACTIVE_DEPLOYMENT_LIMIT`) and nothing changes. Other settings are saved and apply from the next wake.
- **First boot (`provisioning`):** scaling changes apply once the deployment is serving; extra replicas launch after the first one serves. `update` prints a note saying so.
- **`waking`:** no second wake; the new settings apply to the boot in progress, or once it serves.

### Session affinity

- **With `--session-id <key>`** (or the OpenAI `user` field, which sets the `X-Veri-Session-Id` header), a conversation is pinned to one replica so its KV cache stays warm across turns. The same key always lands on the same replica; if that replica is unavailable, the request fails over to another.
- **Without a session key**, requests go to the least-loaded replica.

```bash
veri deployments chat dep_abc -m "Continue our story" --session-id chat-42
```

Reuse the same `--session-id` for every turn of a conversation to keep it on its cache-warm replica.

## Stop to end billing

```bash
veri deployments stop dep_abc
```

`stop` ends billing and is final: a stopped deployment can't wake or resume; bring it back by creating a new one. Running `stop` again on an already stopped (or failed) deployment is a no-op that returns the deployment unchanged. `stop` is not a pause. For a deployment you'll come back to, prefer `--min-replicas 0` and let it park instead.

Once a deployment is stopped (or failed), `veri deployments delete <id>` removes it and its request history for good. Deletion waits for the final billing settlement, so if you delete within a minute of stopping you may be asked to retry shortly.

<Note>
  `start`, `rollback`, and `history` are Phase-2. Each depends on backend work that is not yet shipped.
</Note>

## Inspect traffic

```bash
veri deployments metrics dep_abc
```

Returns aggregate counters: `total_requests`, `total_prompt_tokens`, `total_completion_tokens`, `avg_latency_ms`, `error_rate`, `uptime_seconds`. JSON output is dict-shaped (suitable for `jq`):

```bash
veri deployments metrics dep_abc --format json | jq .avg_latency_ms
```

Recent requests:

```bash
veri deployments requests dep_abc --limit 50
veri deployments requests dep_abc --after req_xyz --limit 100   # pagination
```

Request traces (deployments created with `--trace-bodies` — see the
[traces guide](/deployments/observability#request-traces)):

```bash
veri deployments traces dep_abc --page 1 --limit 20
veri deployments trace dep_abc veri-req000000001    # full request/response bodies
```

## List, get

`list` shows your deployments, most recent first. Filter and paginate with the flags below.

```bash
veri deployments list                              # all of them
veri deployments list --status serving             # only the live ones
veri deployments list --status serving --format json
veri deployments get dep_abc                        # one deployment, with its status
```

| Flag | Purpose |
| --- | --- |
| `--status` | Filter by status: `queued`, `provisioning`, `serving`, `scaled_to_zero`, `waking`, `stopped`, or `failed`. |
| `--limit` | Maximum number to return. Default `20`. |
| `--after <id>` | Pagination cursor: return deployments created after this ID. |

A deployment can hold a GPU while `provisioning`, `serving`, or `waking`, so to catch everything holding one, list without `--status` and scan the `status` column.

With `--format json`, `get` also returns the wake state of a scale-to-zero deployment: `last_wake_at`, `wake_failure_count` and `next_wake_not_before` (see [the deployment object](/deployments/api#post-v1deployments)). When wakes have been failing, the table output adds a line under the table:

```text
Wake: 2 failed wake boots in a row (last wake started 2026-10-03T10:00:00Z); a request wakes it again from 2026-10-03T10:04:00Z, `veri deployments wake dep_abc` retries now.
```

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Success. |
| `1` | User error (both `--model` and `--from-hf` passed, missing `--gpu-type` inline). |
| `2` | API error. |
| `4` | Auth error. |
