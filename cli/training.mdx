Training a model on Veri is a single CLI step: submit a job with `veri jobs create` (or `veri run`). GRPO jobs carry their reward function as a local Python file, attached to the job at submit. Once submitted, manage the job through completion with `list / get / cancel / download`.

<Tip>
  For a script-driven flow, you can also use `veri train <file.py>`: it reads a `@training_job(...)`-decorated function from the file, attaches the decorated function's source as the job's reward, resolves the dataset, and submits the job in one call. See [`veri run`](/cli/run) for the full decorator + TOML reference.
</Tip>

## Reward files

A `method=grpo` job needs a reward function (see [Reward functions](/training/reward-functions) for the contract). Point the config at a local file:

```toml
[reward]
file = "./reward.py"    # resolves against the config file's directory
```

Or pass it from the command line (this overrides `reward.file` in the config):

```bash
veri jobs create configs/train.toml --reward ./reward.py
```

Before submitting, the CLI runs an AST-only structural check on each reward file:

- File parses as valid Python.
- The file defines at least one function.

The check deliberately stops there: verifying the exact signature would require importing user code, which the CLI refuses to do in its own process. If your reward function imports modules missing from the training runtime, the failure surfaces in the training logs once the job starts.

Multiple weighted rewards:

```toml
[reward]
files = ["./correctness.py", "./format.py"]
weights = [1.0, 0.5]
```

Limits: up to 8 files, 256 KiB each. The server re-validates at submit and rejects violations with HTTP 400. The submitted source is stored with the job and viewable on the job's dashboard page.

## Training jobs

| Command | Purpose |
| --- | --- |
| `create <config>` or inline | Submit a training job. |
| `list` | List jobs. |
| `get <id>` | Show one job. |
| `cancel <id>` | Cancel a running job. |
| `download <id>` | Download the completed checkpoint. |
| `delete <id>` | Permanently delete a finished job and its stored checkpoint files. |

### Submit from a config

```bash
veri jobs create configs/train.toml
# or, via the hero verb:
veri run configs/train.toml
```

The config must declare `kind = "train"`. See [`veri run`](/cli/run#configs-train-toml) for the full schema.

`create` returns the job ID. Pipe-friendly form:

```bash
JOB_ID=$(veri jobs create configs/train.toml --quiet)
```

### Submit inline (no config file)

```bash
veri jobs create \
  --base-model "Qwen/Qwen3-4B" \
  --dataset ds_abc \
  --reward ./reward.py \
  --gpu-type A100-80GB \
  --gpu-count 1
```

Inline form requires `--base-model` AND `--dataset`. Pass `--reward` for `grpo`; omit for `sft_video_gen`.

### Override config values

```bash
veri jobs create configs/train.toml \
  --set model.base=Qwen/Qwen3-8B \
  --set method.learning_rate=2e-6 \
  --set resources.gpu_count=4
```

The convenience flags `--base-model`, `--gpu-type`, `--gpu-count`, `--dataset`, `--reward` expand to `--set` internally. See [Override syntax](/cli/run#override-toml-fields-from-the-cli) for type coercion and conflict detection.

### List, get, cancel, delete

```bash
veri jobs list                              # most recent 20
veri jobs list --status running             # filter
veri jobs list --method grpo
veri jobs get job_abc
veri jobs cancel job_abc
veri jobs delete job_abc                    # finished jobs only; removes the stored checkpoint
```

`list` supports `--limit`, `--after`, `--status`, `--method`. All commands accept `--format json`.

### Stream logs

`veri jobs logs` prints everything the job has logged so far (bootstrap and worker output) and exits. Pass `-f`/`--follow` to attach to the live stream until the job reaches a terminal state:

```bash
veri jobs logs job_abc                    # full log so far
veri jobs logs job_abc -f                 # follow until completed/failed/cancelled
veri jobs create configs/train.toml -f    # submit + follow in one step
```

Ctrl+C while following detaches; the job keeps running. Cancel explicitly with `veri jobs cancel`. Following an already-finished job prints its full log.

For scripting, poll status instead:

```bash
while [ "$(veri jobs get $JOB_ID --format json | jq -r .status)" = "running" ]; do
  sleep 30
done
```

### Download a completed checkpoint

```bash
veri jobs download job_abc --output-dir ./checkpoints
```

The download URL is only populated after the job reaches `completed`. Trying to download an in-flight job exits `1` with a clear message.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Success. |
| `1` | User error (missing flag, bad config, failed reward lint, job not downloadable). |
| `2` | API error. |
| `4` | Auth error. |
| `130` | Interrupted: Ctrl+C detached from a followed log stream (the job keeps running). |
